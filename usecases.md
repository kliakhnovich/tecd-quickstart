# T-ECD: идеи задач для курсов, дипломов и исследований

T-ECD можно использовать для проектов по рекомендательным системам, анализу
пользовательского поведения, cross-domain learning и product-aware evaluation.

Этот файл — каталог возможных направлений, а не обязательная программа.  
Большинство идей можно адаптировать под доступные ресурсы: от одного домена из
`small` до нескольких доменов или срезов `full`.

Рекомендуемая точка входа — [`T-ECD_quickstart.ipynb`](T-ECD_quickstart.ipynb):
ноутбук показывает загрузку небольшого среза данных, разбиение по времени,
простые бейзлайны, iALS и базовые метрики.

---

## Как выбрать масштаб эксперимента

| Масштаб | Данные | Ресурсы | Подходит для |
|---|---|---|---|
| Небольшой эксперимент | `small`, один домен, 1–4 недели | ноутбук / Colab, 8–16 ГБ RAM | первые эксперименты, курсовые |
| Средний эксперимент | `small`, один домен или несколько доменов | 16–32 ГБ RAM, GPU опционально | курсовые, дипломы |
| Большой эксперимент | `small` целиком или срезы `full` | GPU / сервер | дипломы, исследования |
| Industrial-scale эксперимент | `full` | кластер / многокарточная конфигурация | исследовательские работы, масштабируемость |

Если задача не помещается в память, обычно помогает уменьшать объём в таком порядке:

1. взять один домен;
2. сократить временное окно;
3. оставить top-N активных пользователей;
4. оставить top-N популярных товаров;
5. читать только нужные колонки из parquet-файлов.

## Основные направления

| Направление | Идея | Формат |
|---|---|---|
| Cross-domain recommendations | Использовать поведение пользователя в одном домене для рекомендаций в другом | диплом / исследование |
| Surface-aware recommendations | Сравнить обучение на событиях из поиска, каталога и рекомендательных блоков через `subdomain` | диплом / исследование |
| Action types as implicit feedback | Изучить, как разные действия `view`, `click`, `clickout`, `like` влияют на обучение и оценку моделей | курсовая / диплом |
| Cold start and hybrid recommendations | Строить рекомендации для новых пользователей и товаров, используя user/item side information и fallback-стратегии | курсовая / диплом |
| Popularity bias and diversity | Исследовать смещение моделей к популярным товарам и trade-off между accuracy, coverage и diversity | курсовая / диплом |
| Candidate generation + ranking | Построить двухэтапную рекомендательную систему: генерация кандидатов и ранжирование с implicit feedback | курсовая / диплом |
| Temporal / recency-aware recommendations | Изучить влияние свежести истории, длины train window и временного дрейфа на качество рекомендаций | диплом / исследование |

# Идеи задач

## 1. Cross-domain recommendations

**Идея.**  
T-ECD содержит несколько доменов с пересекающимися пользователями. Это позволяет
изучать перенос поведения между доменами без искусственного склеивания разных
датасетов.

**Что можно исследовать:**

- помогает ли активность в одном домене улучшить рекомендации в другом;
- какие пары доменов дают положительный transfer;
- когда перенос знаний ухудшает качество;
- помогает ли cross-domain сигнал новым пользователям целевого домена;
- как меняется качество при добавлении нескольких source-доменов.

**Возможный формат эксперимента:**

- train on domain A → test on domain B;
- train on A + B → test on B;
- single-domain baseline vs multi-domain model;
- отдельная оценка на пользователях с разной активностью;
- матрица transfer-качества между доменами.

**На что обратить внимание.**  
Item spaces в разных доменах могут отличаться, поэтому cross-domain постановка чаще
связана не с общим каталогом товаров, а с переносом пользовательского поведения и
user representations между доменами.

**Ресурсы.**  
Несколько доменов из `small`; для больших экспериментов — срезы `full`. GPU желателен.

---

## 2. Surface-aware recommendations

**Идея.**  
В T-ECD есть поле `subdomain`, которое позволяет различать поверхности взаимодействия:
например поиск, каталог, рекомендательные блоки и другие сценарии. Это позволяет
исследовать, как источник события связан с будущим качеством рекомендаций.

**Что можно исследовать:**

- различается ли поведение пользователя в поиске, каталоге и рекомендациях;
- как меняется модель, если обучаться только на событиях из определённых `subdomain`;
- как source-specific weighting влияет на `HitRate@k`, `NDCG@k`, `Coverage@k`;
- отличаются ли категории и популярность товаров между поверхностями;
- дают ли события из разных поверхностей разный сигнал для будущих рекомендаций.

**Возможные сравнения:**

- обучение на всех событиях;
- обучение только на поисковых событиях;
- обучение только на каталоге;
- обучение только на рекомендательных поверхностях;
- разные веса для разных `subdomain`.

**На что обратить внимание.**  
Такой анализ может быть полезен для изучения эффектов, связанных с feedback loop,
но датасет не содержит полного causal logging: показов, позиций, идентификаторов
моделей и рандомизации. Поэтому выводы лучше интерпретировать как offline-анализ
связи между источником события и качеством модели, а не как причинный эффект.

**Ресурсы.**  
`small` целиком или несколько доменов; 32+ ГБ RAM, GPU опционально.

---

## 3. Action types as implicit feedback

**Идея.**  
T-ECD содержит разные типы действий: `view`, `click`, `clickout`, `like`.
Они могут нести разный уровень пользовательского интереса. Это позволяет исследовать,
как выбор target-события влияет на качество рекомендаций.

**Что можно исследовать:**

- обучаться только на `view`;
- обучаться только на `click`;
- обучаться на `clickout` или `like`;
- использовать взвешенную смесь событий;
- оценивать модель на более сильном сигнале, чем тот, на котором она обучалась;
- сравнить качество и coverage при разных схемах весов;
- проверить, одинаково ли это работает в разных доменах.

**Пример схемы весов:**

```text
view     → 1
click    → 2
clickout → 3
like     → 4
```

**Примеры вопросов:**

- помогает ли большое количество `view`-событий или добавляет шум;
- лучше ли обучаться на слабом сигнале, а оценивать на сильном;
- какие события дают лучший баланс accuracy и diversity;
- насколько редкие, но сильные действия полезны для обучения.

**Ресурсы.**  
`small`, один домен, 30+ дней; 16+ ГБ RAM.

## 4. Cold start and hybrid recommendations

**Идея.**  
В T-ECD достаточно новых пользователей и товаров относительно временного train/test
разбиения, есть анонимные признаки пользователей, а для части товаров доступны
категории, бренды и контентные эмбеддинги. Это позволяет исследовать реалистичные
cold-start и hybrid-сценарии, включая неполное покрытие side information.

**Что можно исследовать:**

- рекомендации для новых пользователей;
- рекомендации для пользователей с короткой историей;
- рекомендации для новых товаров;
- различия между warm-start и cold-start качеством;
- content-based рекомендации на товарах с доступными признаками;
- fallback-стратегии для товаров без side information;
- гибрид collaborative filtering + content/user features.

**Для пользователей можно использовать:**

- регион;
- соцдем-кластер;
- популярность в сегменте;
- первые несколько действий пользователя.

**Для товаров можно использовать, если признаки доступны:**

- категорию;
- подкатегорию;
- бренд;
- контентные эмбеддинги;
- похожесть на товары с историей.

**Возможные подходы:**

- global и segment-aware `TopPopular`;
- category/brand popularity;
- item-to-item similarity по эмбеддингам;
- content-based user profile;
- гибрид iALS + content similarity;
- fallback на `TopPopular` для объектов без признаков.

**На что обратить внимание.**  
Item features доступны не для всего каталога, поэтому полезно отдельно считать качество:

- на всех товарах;
- на товарах с доступными признаками;
- на товарах без доступных признаков;
- на warm-start и cold-start пользователях;
- на head и long-tail товарах.

**Ресурсы.**  
`small`, один домен, каталог товаров; 16+ ГБ RAM, GPU опционально.

## 5. Popularity bias and diversity

**Идея.**  
В реальном e-commerce популярные товары часто доминируют в рекомендациях. Такая модель
может показывать хорошую точность, но давать однообразную выдачу и плохо покрывать
long tail каталога.

**Что можно исследовать:**

- насколько разные модели смещены к популярным товарам;
- как меняется `Coverage@k` у `TopPopular`, iALS и других моделей;
- какую долю рекомендаций занимают товары из head / torso / tail;
- как re-ranking влияет на accuracy и diversity;
- отличается ли popularity bias между доменами;
- как bias меняется для разных групп пользователей.

**Возможные метрики:**

- `HitRate@k`;
- `NDCG@k`;
- `Coverage@k`;
- доля long-tail товаров в рекомендациях;
- category diversity;
- intra-list diversity;
- novelty.

**Ресурсы.**  
`small`, один домен, 30+ дней; обычно достаточно 16+ ГБ RAM.

## 6. Candidate generation + ranking

**Идея.**  
Многие промышленные рекомендательные системы устроены в два этапа:

1. быстрая модель генерирует кандидатов;
2. ранжирующая модель переупорядочивает кандидатов.

T-ECD можно использовать для прототипа такой схемы на implicit feedback.

**Candidate generation:**

- `TopPopular`;
- ItemKNN;
- iALS;
- ANN-поиск по эмбеддингам товаров;
- похожие товары по категориям или контентным эмбеддингам.

**Ranking:**

- логистическая регрессия;
- градиентный бустинг;
- простая нейросетевая модель;
- learning-to-rank подходы.

**Признаки для ranking:**

- признаки активности пользователя;
- признаки популярности товара;
- признаки категории или бренда;
- агрегаты за разные временные окна;
- свежесть последних взаимодействий;
- признаки по `action_type` и `subdomain`;
- признаки на парах пользователь × категория.

**Что можно исследовать:**

- recall candidate generator;
- сколько кандидатов нужно для хорошего качества;
- какие признаки полезны ранкеру;
- насколько ranking улучшает iALS или `TopPopular`;
- trade-off между скоростью и качеством.

**На что обратить внимание.**  
T-ECD содержит логи взаимодействий, но не является полным логом показов. Поэтому
для обучения ранкера обычно используются positive interactions и sampled negatives.
Такие negatives лучше интерпретировать как незафиксированные пары user-item, а не
как настоящие просмотры без клика.

Также важно считать признаки только по прошлым событиям. Если модель ранжирует
кандидатов для периода, начинающегося в день `D`, все агрегаты должны быть посчитаны
только по событиям до `D`.

**Ресурсы.**  
`small`, один домен, 30+ дней; 16–32 ГБ RAM, GPU желателен.

## 7. Temporal / recency-aware recommendations

**Идея.**  
В T-ECD сохранена временная структура событий. Даже если порядок событий внутри дня
не всегда достаточно детален для session-level sequential modeling, данные хорошо
подходят для изучения temporal recommendation: влияния свежести сигналов, длины
истории и временного дрейфа.

**Что можно исследовать:**

- лучше ли обучаться на всей истории или только на последних N днях;
- как recency weighting влияет на качество;
- насколько быстро устаревает популярность товаров;
- помогает ли разделение истории на дневные или недельные пользовательские корзины;
- как меняется качество при разных train/test окнах;
- отличаются ли оптимальные временные окна между доменами;
- насколько стабильны выводы при sliding window evaluation.

**Возможные подходы:**

- `TopPopular` за последние N дней;
- iALS с весами по свежести событий;
- user/item/category features за разные временные окна;
- next-period recommendation;
- модели на агрегированных daily/weekly histories;
- сравнение качества и разброса метрик на нескольких временных окнах.

**Опционально.**  
Если в выбранном срезе получается надёжно восстановить порядок событий, можно
дополнительно попробовать sequential-модели. Но базовая постановка не должна
зависеть от точного порядка событий внутри дня.

**Ресурсы.**  
`small`, один домен или несколько доменов; 16–32 ГБ RAM, GPU опционально.

## Advanced extension: scalability from `small` to `full`

**Идея.**  
Метод, который хорошо работает на небольшом срезе, не всегда переносится на большие
данные. T-ECD позволяет проверять качество и стоимость метода при росте объёма данных.

**Что можно исследовать:**

- как меняется качество при увеличении числа пользователей, товаров и событий;
- как растёт время обучения;
- как растёт потребление памяти;
- сохраняется ли ranking моделей при переходе от `small` к `full`;
- какие методы дают лучший trade-off между качеством и ресурсами.

**Возможный формат:**

- маленький срез `small`;
- больший срез `small`;
- несколько доменов;
- срез `full`;
- полный `full`, если доступны ресурсы.

**Ресурсы.**  
GPU-сервер или кластер; для `full` может потребоваться распределённое обучение.

## Несколько практических замечаний

Для рекомендательных систем обычно лучше использовать разбиение по времени:

```text
train      — прошлое
validation — ближайшее будущее
test       — следующий период
```

Случайное train/test-разбиение может завышать качество, потому что в train попадают
события из будущего.

В качестве стартовых бейзлайнов удобно использовать:

- `Random`;
- `TopPopular`;
- `TopPopular` за последние N дней;
- iALS.

Помимо accuracy-метрик вроде `HitRate@k` и `NDCG@k`, часто полезно смотреть на:

- `Coverage@k`;
- diversity;
- novelty;
- долю long-tail товаров;
- качество по сегментам пользователей;
- качество по warm-start и cold-start группам.

При обучении ranking-моделей важно помнить, что незафиксированное взаимодействие
не равно настоящему негативному примеру: обычно это sampled negative, а не
достоверный non-click.

Для анализа `subdomain` стоит избегать причинных формулировок, если не используются
логи показов, позиции и рандомизация. Лучше интерпретировать такие эксперименты как
offline-анализ связи между источником события и качеством модели.
